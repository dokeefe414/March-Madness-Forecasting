# Nightly capture and Pages recovery — November 18, 2026 incident

**Scope:** Restoration and hardening of the existing source-backed 2026–27
college basketball archival and static-site automation. The active Elo formula,
trained models, original pregame probabilities, settlement rule, and public
prediction history are NOT modified by this recovery.

## Observed failure: what we actually verified

1. The **scheduled site refresh**
   [run #44413144199](https://github.com/dokeefe414/March-Madness-Forecasting26-27/actions/runs/44413144199)
   completed all score/model/data generation and the static Next build.
   `actions/upload-pages-artifact@v3` uploaded the `github-pages`
   artifact, but the very next Pages API lookup reported that *no* artifact
   existed. The GitHub Actions artifacts API **did** later list the artifact
   under the same run ID. This is an artifact-visibility/API race, not an
   identified Python model/build failure.
2. Retrying only the failed job within the **same run** uploaded a second
   artifact with the *same name* into that run. Pages then failed because
   there were **two** `github-pages` artifacts. A same-run job retry
   therefore cannot be the automated recovery mechanism.
3. The [archive monitor #44416835619](https://github.com/dokeefe414/March-Madness-Forecasting26-27/actions/runs/44416835619)
   correctly observed a stale archive: last committed capture
   `2026-11-18T16:20:31Z`. The archive workflow had only a prior successful
   `push` run visible, and no scheduled capture for the expected afternoon
   slot. The exact reason GitHub did not create that `schedule` event is
   not proven. GitHub itself says scheduled events can be delayed or
   dropped. We should not claim it was a forecast-model error.

## Repair design

### Archive: separate native schedules and an independently scheduled watchdog

`archive-pregame.yml` preserves 2:07, 6:07, 9:07 and 16:07
**America/New_York**, November–April, but uses **four explicit cron
objects** instead of one multi-hour object. Changing this file also
re-registers the workflow schedule in GitHub's default-branch scheduler
and triggers one immediate source-safe `push` archive after merge.

`monitor-archive.yml` independently runs at 3:41, 7:41, 11:41, 18:41
Eastern and also when a Pages deployment succeeds. It checks the committed
Git forecast ledger with a four-hour freshness limit; if stale or missing:

1. Check whether an archiver is already queued/in progress. If so, do not
   create another duplicate.
2. Otherwise, call `gh workflow run archive-pregame.yml --ref main`
   with a narrowly scoped `GITHUB_TOKEN` (`actions: write`).
   GitHub explicitly permits `workflow_dispatch` generated by the
   repository token to start a workflow, even though token-produced Git
   pushes generally do *not* trigger other workflows.
3. Retain a visibly failed monitor and one deduplicated open GitHub
   incident issue while archive evidence is stale. After a subsequent
   genuinely fresh archive **and successful immutable audit**, close the
   old issue with a recovery note. Failed audit never causes a blind
   resnapshot: dispatch only when the **freshness** step failed.

This is a bounded self-repair *trigger*, not permission to overwrite
an already issued forecast. `forecast.snapshot` only captures still-future
ESPN fixtures with verified as-of score timestamps and independently confirms
ESPN `STATUS_FINAL` plus matching NCAA scores before settlement. Missing
sources leave original picks pending, not invented results. All archive
commits use regular safe rebase/push without force.

### Pages: avoid missing metadata and prevent same-run artifact duplication

`deploy-pages.yml` now:

1. Builds all existing research, game, rating, calibration and site artifacts
   as before.
2. Uploads **exactly one** `github-pages` artifact.
3. With `actions: read`, queries the **current run's** artifact list up to
   18 times, ten seconds apart, until exactly one nonexpired
   `github-pages` artifact is visible. Reject zero forever or duplicates.
   Allow a short propagation delay after visibility is confirmed.
4. Starts `actions/deploy-pages@v4` with a longer 15-minute operation
   timeout and up to 20 API errors to tolerate transient metadata misses.

Independent `recover-pages.yml` runs **only** when a Pages workflow ends in
failure. Its narrowly scoped token checks that **the only failed step**
was `Run actions/deploy-pages@v4` and **one** uploaded, unexpired
`github-pages` artifact exists on that failed run. It then launches a
**new workflow_dispatch run** of `deploy-pages.yml` on `main`—not
`rerun-failed-jobs`. This avoids mixing two artifacts under one run ID.
It never retries failed source/data/model or build steps and never
dispatches again if the failed run was itself a `workflow_dispatch`,
or the attempt number is greater than one. Persistent failures remain
visible and require review.

### Honest limitations

- GitHub's first-party cron is still best-effort. A delayed scheduler,
  GitHub API outage affecting *both* primary and watchdog schedules, or a
  provider outage can still require manual investigation. Nothing in
  GitHub Actions guarantees an update immediately after every game.
- A watchdog dispatch succeeding means an archive **was requested**, not
  that it completed successfully. Later green archive and monitoring
  evidence is needed before declaring health restored.
- A source file having scores does not independently prove that an ESPN
  event reached a final state; archival settlement retains the original
  double-source verification contract.
- Current-season website research recalculates on schedule but challenger
  promotion remains manual/scientific-review only.
- A Pages artifact passing the Actions API check can still fail the
  downstream Pages API; only successful deployment proves publication.
- In-season 2027 model accuracy is not guaranteed to improve.

## Verification and response workflow

1. Ensure both [archive Actions](https://github.com/dokeefe414/March-Madness-Forecasting26-27/actions/workflows/archive-pregame.yml)
   and [Pages Actions](https://github.com/dokeefe414/March-Madness-Forecasting26-27/actions/workflows/deploy-pages.yml)
   have new successful jobs **after** the change is merged.
2. Verify [monitor](https://github.com/dokeefe414/March-Madness-Forecasting26-27/actions/workflows/monitor-archive.yml)
   runs and that the last capture's `generatedAtUtc` increases (not just
   that the site build is green).
3. On a missing archive, inspect the watchdog job's
   `Dispatch verified original-first-pick archive after missing capture`
   step, then look for a `workflow_dispatch` archive job on `main`.
4. If Pages fails at its deploy-only step, inspect
   [Pages recovery](https://github.com/dokeefe414/March-Madness-Forecasting26-27/actions/workflows/recover-pages.yml)
   for a new, distinct workflow ID. **Do not manually rerun the
   same failed Pages job** after it uploaded `github-pages`: that is known
   to produce duplicate artifacts.
5. If the watchdog cannot recover, open the live workflow logs and the
   deduplicated `Forecast archive health needs attention` issue. When
   sources are down, leave already frozen picks intact and retry later.

## Reproducible checks

```powershell
$env:PYTHONPATH="research"
py -m unittest discover -s research/tests -p "test_nightly_automation.py" -v
py -m unittest discover -s research/tests -p "test_archive_health.py" -v
py -m unittest discover -s research/tests -v
py -m forecast.archive_health --ledger web/public/forecasts --out web/public/current/archive-health.json
py -m forecast.audit --dir web/public/forecasts
```

The static contract tests prove the configured triggers and recovery guards;
they **do not** prove GitHub will deliver every future schedule. Only actual
GitHub runs and committed source-backed artifacts can establish operational
success.
